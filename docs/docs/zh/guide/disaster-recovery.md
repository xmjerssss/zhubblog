# 灾难恢复指南：账号没了，博客还在

这份文档只讲一件事：**Cloudflare 账号整个废掉（或者误删了 Worker / D1 / 域名）之后，怎么用「一个全新的账号 + 原来那个存储桶」把博客一模一样地救回来。**

> 一句话结论：只要存储桶还在、桶里有备份文件、图片视频还躺在桶里，内容就能 100% 回来。
> 找不回来的只有环境变量里那几样东西（密钥、域名、OAuth 应用），需要在新账号里重新配一遍。

---

## 一、备份里到底有什么

每次备份都是一份完整的 JSON，`POST /api/backup/export-to-storage` 写到桶的 `backups/` 目录，最多滚动保留 3 份。

| 数据 | 是否进备份 | 说明 |
| --- | --- | --- |
| 文章、动态、友链、评论、标签、文章标签关联 | ✅ | 全部内容 |
| 站点配置（站点名、主题、评论开关、公告……） | ✅ | 恢复后站点外观一致 |
| 用户（含站长、GitHub `openid`、密码哈希） | ✅ | PBKDF2 哈希可跨账号使用，密码登录能直接用 |
| 自定义存储配置 + 文件索引 | ✅ | 文件索引进备份，**文件本体一直在桶里** |
| 访问统计与明细（`visit_stats` / `visits`） | ✅ | IP 存的是哈希；明细只带最近 2 万条，PV/UV 汇总完整 |
| 环境变量（`JWT_SECRET`、`S3_*`、`RIN_GITHUB_CLIENT_*`、域名） | ❌ | 不属于数据，需在新账号重新配置 |
| 自定义存储的 SecretKey、GitHub 备份 token | ⚠️ | 随备份走，但用旧主密钥加密，换账号后需重填 |

从 v0.3.0 起 Worker 的定时任务每天会往桶里写一份快照（`backups/rin-backup-*.json`），所以桶里一定有一份不超过 24 小时的备份。想调整频率，在 `server.config` 里设 `backup_auto_interval_hours`（小时，`0` 关闭）。

## 二、备份之前（还在用的时候）

1. 打开后台 →「设置 → 备份」，点一次**导出到云存储**，确认桶里出现 `backups/rin-backup-*.json`。
2. 记下三个东西（建议存密码管理器）：
   - 存储桶的 `endpoint` / `bucket` / `AccessKey` / `SecretKey`；
   - 站点的 `JWT_SECRET`、`S3_FOLDER`；
   - 你登录后台用的是「账号密码」还是「GitHub OAuth」。
3. 如果用的是自定义存储（R2/S3/WebDAV 填在后台里而不是环境变量），额外记下 `STORAGE_SECRET`：
   设置成固定值后，换账号恢复时旧密钥也能解开，省去重填。

## 三、灾难恢复步骤

### 第 1 步：新账号里重建 Worker

1. 在**新账号**里 fork 仓库，按 [部署指南](/guide/deploy) 创建 D1 数据库、R2（或继续用外部 S3/WebDAV）。
2. 在 Workers → Settings → Variables 填环境变量。**关键三条**：
   - `JWT_SECRET`：可以换新的，但换了以后「自定义存储密钥 / GitHub token」要重填；
   - `S3_ENDPOINT` / `S3_BUCKET` / `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY`：指向**原来那个存储桶**；
   - `S3_FOLDER`：必须和出事前**完全一致**（例如 `images/`），否则图片路径会错位。
3. 打开站点，用初始化时的站长账号登录后台。

> 如果图片不在这个桶里，而是另一个自定义存储：先在「设置 → 存储管理」里把它加回来（endpoint/bucket/AccessKey 都填原来的，SecretKey 重新填一次即可，配置本身也在备份里）。

### 第 2 步：从桶里恢复

后台 →「设置 → 备份 → 从云存储恢复」，填桶里的备份路径（例如 `backups/rin-backup-2026-01-01T10-00-00.json`），确认后执行。

恢复过程会：

1. 先校验备份文件结构，**文件不对就直接报错退出，现有数据一行都不动**；
2. 把当前数据库的内容另存一份到桶里的 `backups/pre-restore.json`（恢复失败还能退回去）；
3. 清空并重写全部业务表（文章/评论/友链/配置/存储/访问数据）；
4. **保住你当前登录账号的管理员身份**——即使备份里的站长是另一个 GitHub 账号，恢复后你仍然是管理员；
5. 清空服务端缓存，回读数据库告诉你真实恢复了多少条。

恢复完成后页面会弹出一份报告：文章/评论/动态/友链/文件数量、`pre-restore.json` 的位置，以及还需要手动处理的提示（例如「某自定义存储的密钥无法解密，请重填」）。

### 第 3 步：收尾检查

| 检查项 | 预期 |
| --- | --- |
| 首页文章、分页、标签 | 与出事前一致 |
| 站点名称/图标/主题 | 与出事前一致（`site.*` 配置已恢复） |
| 文章里的图片 | 能正常显示（文件索引已恢复，文件本体在桶里） |
| 后台 → 存储管理 | 若有「密钥无法解密」提示，重填 SecretKey |
| 访问统计 | 历史 PV 已恢复，新访问继续累加 |
| 评论/友链/动态 | 全部存在 |
| GitHub 备份（如本来在用） | token 需重填一次 |
| `RIN_GITHUB_CLIENT_ID/SECRET` | 在新账号重建 OAuth App 后更新，回调地址不变 |

## 四、常见问题

**Q：新账号的 `storages` 表是空的，会不会恢复不了？**
不会。恢复入口会依次尝试：环境变量里的默认存储 → 数据库里可用的自定义存储 → 其他还能解密的存储。只要 `S3_*` 指向那个桶，即使数据库一条存储配置都没有，也能直接恢复。

**Q：提示「存储密钥无法解密」怎么办？**
因为 `STORAGE_SECRET`（没设的话是 `JWT_SECRET`）变了。两种解法：把 `STORAGE_SECRET` 设成出事前的值；或者到「存储管理」里把该存储的 SecretKey 重新填一次。这期间默认存储（环境变量）照常可用，图片不会全挂。

**Q：恢复会不会把我新账号里刚写的东西覆盖掉？**
会。所以恢复前会自动写 `backups/pre-restore.json`，需要的话把它当普通备份再恢复一次即可。

**Q：没有备份文件怎么办？**
那就只能靠 GitHub 备份（如果配过）或本地导出的 JSON。**备份要在出事之前做**——这也是自动备份默认开启的原因。

**Q：为什么我的访问明细（`visits`）比出事前少？**
两个原因，都属预期：一是快照之后新产生的访问记录不在备份里；二是明细本身只备份最近 2 万条（热门站点动辄上百万行，全塞进 JSON 会让备份文件暴涨、恢复变慢）。文章 PV/UV 汇总数据是完整的，阅读量数字不受影响，恢复完成时也会提示被省略了多少条。

```bash
cd server
bun test src/services/__tests__/backup-disaster-recovery.test.ts
```
